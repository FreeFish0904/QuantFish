3　一次提交走过什么路径

  1. 上传与入队。POST /api/submissions 校验脚本（接口约定、语法、导入）， 写入运行时仓储并把任务置为 queued；同队冷却时间与评分超时都来自同一份配置。
  2. 独立进程评分。SubmissionScoringDispatcher 在 max_concurrent_scoring 上限内起一个 score_worker 子进程， Web 进程不被计算阻塞；进度可轮询、可中止。
  3. 构建面板。CSMAR 风格原始表按 as-of 语义 join，用 cumulatefwardfactor 做前复权，再按市场类型、上市天数与交易状态过滤； 结果缓存进 panel_cache，同一份数据的重复运行不必重算。
  4. 撮合与评估。t 日的信号在 t+1 的 VWAP 成交， 叠加涨跌停、停牌、参与率上限与交易成本；行业中性化后分五组， long-only 模式按排名加权，并给出相对 HS300 的 beta 调整主动收益。
  5. 算指标。指标只在一个地方算：quantfish.backtest.metrics。 同一份日收益序列同时导出算术口径（用于打分）与几何口径（用于报告），两者永不混用。
  6. 交付产物。summary.csv、graph_data.json、 分年 performance_by_year.csv、parquet 序列与可选 PDF 报告； UI 直接渲染这些产物，并在配置或数据发布变化后把旧运行标成 stale。

两条关键的设计约束

约束为什么必须这样
算子进程隔离 学生代码质量不可控（死循环、内存暴涨、sys.exit）；子进程 + 超时是唯一 能保证 Web 一直可用的做法，错误原文也正好可以回传给详情页。
时点正确（不偷看未来） 面板按 as-of 语义构建、信号次日成交、复权因子只使用当日及之前的信息， 否则回测会系统性高估。
口径唯一 指标一处计算、多处展示：summary.csv → SubmissionMetrics → 详情页 / PDF。任何界面都不会自己再算一遍年化。
可复现性：每次运行都会留下配置指纹与数据发布指纹。 参数一改、数据一换，历史运行立刻变成 stale，而不是被当成可比结果继续排名。
